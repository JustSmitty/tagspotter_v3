The maintainer chose removal over relabelling. `StateService` now writes the snapshot as plain JSON.
The AES-GCM envelope, the key derivation, and both base64 helpers are gone from the write path.

**Why removal was the right half of dec-0005:** the key came from a password and salt hardcoded in
the shipped bundle, so it stopped nobody, and con-0004-no-backend-no-accounts means no one is harmed
by a player editing their own save. Keeping it would have preserved a per-write cost and, worse, a
line of code that reads like a security control to the next person who opens the file.

## The part that matters most

Removal could not be a straight deletion. Players on <= 1.1.0 have an encrypted blob on their device,
and dropping the read path would have silently reset their trip on upgrade.

So `LegacySaveReaderService` reproduces the old constants for **decryption only**. `StateService`
rewrites anything it reads through that path as plain JSON, so each device migrates once and never
touches it again. Both legacy shapes are covered: the v2 `{version, ciphertext}` envelope and the
pre-v2 raw base64 with a detached `_sig` key.

`guardrail:crypto-theater` excludes that one file by path, with the reason recorded inline. **Delete
the service, the exclusion, and this paragraph once no supported upgrade path starts below 1.2.0.**

## Testing note

Both `legacy-save-reader.service.spec.ts` and the storage block in `state.service.spec.ts` generate
ciphertext the same way v1.1.0 generated it, rather than asserting against a checked-in fixture. A
fixture can be regenerated by someone who does not realise it encodes a compatibility contract; a
reproduction of the original algorithm cannot drift without the drift being visible.
